# 講演用の進行 v5

四つの実演を、同じ冷却器1の事例で行う。別設備と全12件は自由体験用であり、本編では一つずつ紹介しない。

## 事前準備

新しいv5練習領域を明示的に作り、初期12件・文書6/Q&A6を確認する。既存領域の上書きで準備しない。対象文書・模擬回答は入力支援欄に用意するが、未送信のままLLMへ見せない。講演者の作業領域を参加者と分ける。混雑を避けるため、主実演時は参加者には閲覧、終了後に自由対話を案内する。

モデル・prompt・検索設定を固定し、必要なAPI枠を確認する。例の計器確認は架空の教材設定であり、現場の操作推奨ではないと断る。

## 導入：既にある知識を探す（約30～45秒）

1. `知識を探す`で12件の件数と由来を見せる。
2. `冷却器1 流量低下`と検索する。
3. 文書かQ&Aを一つ開き、要点と原文を示す。
4. 「このように知識がある状態に、今回の事例を追加します」とつなぐ。

これはLLMの生成デモではなく、実際の保存知識に対する通常検索である。

## デモ①：文書から取り出す（目安1分30秒）

保全記録1を入力・抽出し、原文と照合して承認する。文書だけでは当時の冷却水側の状態・詳しい判断理由・参照範囲は十分に分からない点を示す。

同じ画面の「比較用の質問を実行（APIを使用）」から、空履歴で主質問への実回答Aを取得する。この場では詳細を読まず、文書版の記録として保存する。準備時に実行したAを利用する場合は「事前に取得した実行記録」と示し、時刻・設定・同一対象を確認する。

## デモ②：対話で聞き出す（目安2分30秒）

1. 本人役の開始発言に、交換直後だったこと・照合したこと・冷却水側通常だったことを入れる。
2. 実際の質問に合わせ、判断理由を回答する。
3. 実際の質問に合わせ、経験を参照する条件と例外を回答する。
4. 追加の理由・条件・出典を見て、一度のレビューで新版を承認する。

入力例は提案であり、画面の質問と違う内容なら講演者が回答を調整する。「分からない」もそのまま記録できることを説明する。
画面に自動入力される開始発言と本人役の回答例は、アプリに固定収録した架空教材でありLLM生成ではない。LLM生成の追加質問とは表示上も説明上も区別する。理由用・適用範囲用の固定回答例を一度ずつ使った後は自動挿入されない。LLMが聞き取り完了を返した場合、追加回答を強制せず補足案の作成へ進む。

## デモ③：検索して使う（目安3分30秒）

1. 空の新しいQA会話で、Aと同じ主質問を実行し、Bを取得する。
2. A/Bを並べ、対象の行動が同じでも、Bには本人役が述べた理由・参照範囲・新出典があるかを確認する。
3. `なぜこの確認が候補になるのですか` または `流量が下がっていた場合も同じですか` を一問だけ続ける。
4. 原文と条件の違いを確認する。事例2等の初期知識が使われた場合はその出典を示す。

A/Bの文言が変わっただけを成果にせず、どの新しいfactと根拠が参照されたかを説明する。差が出なければその結果を示し、原因をログで確認する。

## デモ④：フィードバックで直す（目安3分30秒）

1. Bの実候補の「根拠・条件を補足する」から、校正有効性を確認する必要を入力する。
2. 新しい原文と更新差分を見せる。未承認なので、正式な検索対象はまだ前の版。
3. 人が承認し、同じ主質問を空履歴で再実行してCを得る。
4. Cに追加条件と聞き取り記録2が使われたかを示す。B/Cの差分は1点だけ説明する。

「校正が有効だった」ではなく「校正が有効か確認する」という前提の追加であることを強調する。

## 時間・障害への対応

上記時間は配分目安であり保証ではない。実APIリハーサルで測定する。予定を超えた場合は自由対話の追質問を省略し、承認境界や根拠確認を省略して成功扱いしない。

エラーなら停止してエラーとして説明する。録画や図解へ移る場合は講演者が明示し、アプリが自動的に模範回答へ切り替えたようにしない。比較記録がない部分をその場で作った固定文で埋めない。
