# WG4デモアプリ 参加者向け操作ガイド

**講演：AIエージェントによる暗黙知と形式知の構造化・活用の第一歩**
**開催日：2026年9月17日**

アプリ：<https://wg4-demo-kato.streamlit.app/>

## 1. このデモで体験できること

架空の製造設備事例を使い、次の流れを体験できます。

1. 蓄積済みの文書・Q&Aから知識を探す
2. AIエージェントへ相談し、確認候補・条件・理由・原文を確かめる
3. 保全記録から知識候補を抽出する
4. 本人役への追加質問で、判断理由や適用条件を補う
5. 人が内容を承認した後、新しい知識版を相談に利用する

> このアプリの設備・記録・発言はすべて架空の教材です。実設備の操作判断には使用しないでください。

> **結果の見方：** LLMが作る文章や追加質問の細かな言い回しは実行ごとに変わることがあります。以下の「期待される結果」では、文章の一致ではなく、知識の版、factの種類、未確認事項、原文、処理状態を照合してください。

## 2. 利用前の注意

- 参加者パスワードは講演者から別途案内します。OpenAIのAPIキーは不要です。
- 実在する企業名、個人情報、機密情報、実設備の非公開情報を入力しないでください。
- 各参加者の作業領域は分離されています。他の参加者の会話や更新案は表示されません。
- 作業領域はデモ用の一時領域です。恒久的な保存場所として使用しないでください。
- API処理には待ち時間が生じることがあります。同じボタンを続けて押さないでください。

## 3. ログイン

1. アプリを開きます。
2. 案内された参加者パスワードを入力します。
3. ログイン後、参加者ごとの練習用作業領域が作成されます。
4. 初期状態では、架空の知識12件（文書6件、Q&A 6件）が登録されています。

**期待される結果**

- サイドバーに`モデル: gpt-5.6-luna / 推論: medium / KB改訂: 1`と会話IDが表示される
- `知識を探す`に`知識項目 12`、`文書 6 / Q&A 6 / 混合 0`、`設備 3`と表示される
- 自分専用の作業領域が作られ、他の参加者のデータは表示されない

## 4. 画面の構成

| 画面 | できること |
|---|---|
| `知識を探す` | 承認済み知識を無料で検索し、原文と版を確認する |
| `エージェントに相談する` | 現行の承認済み知識を検索し、根拠付きの候補を得る |
| `知識を追加・補足する` | 文書抽出と、本人役への追加質問を行う |
| `更新案・実回答比較` | 更新差分を承認し、回答A/B/Cを比較する |

## 5. まず知識を探す

1. `知識を探す`を開きます。
2. 検索語へ次を入力します。

   ```text
   冷却器1 流量低下
   ```

3. 必要に応じて設備や由来（文書／Q&A／文書＋Q&A）を選びます。
4. `検索する（API不使用）`を押します。
5. 検索結果で次を確認します。
   - 知識名と版
   - 設備と由来
   - 登録されている事実・条件
   - `原文と版を確認`内の元文書または本人役の回答

`この知識について相談する`を押すと、その知識を選んだ状態で相談画面へ移動できます。

**期待される結果**

- 現在の初期教材では検索結果が8件表示される
- 上位に、Q&A由来の`流量が低い相談で不足条件を尋ねる理由`と、文書由来の`冷却水流量の表示低下を伴った事例`が含まれる
- 文書とQ&Aの両方で、知識項目、`v1`、fact、未確認事項、原文を確認できる
- 通常検索だけではOpenAI APIを使用せず、画面に`完了（操作ID ...）`は新たに表示されない

## 6. エージェントに相談する

1. `エージェントに相談する`を開きます。
2. 次の質問を入力します。

   ```text
   冷却器1の出口温度の表示が高いです。何を確認すればよいですか。
   ```

3. `現行知識を調べて相談する（APIを使用）`を押します。
4. 回答で次を確認します。
   - 確認候補
   - 適用条件・行動前提
   - 判断理由・例外・未確認事項
   - 参照した知識項目と版
   - 原文の根拠
   - 関連する知識グラフ
   - 実行したツール

続けて、例えば次のように質問できます。

```text
なぜこの確認が候補になるのですか。
```

```text
流量が下がっていた場合も、同じ確認でよいですか。
```

`新しい会話（知識は残す）`を押すと、質問履歴と相談条件だけが消えます。承認済み知識は残ります。

> 相談中の発言は、承認なしに正式知識へ登録されません。

**期待される結果**

- 最初の質問では、`知識項目1 v1`などの承認済み知識を根拠に、同時刻の温度・流量・運転区分をそろえる確認候補が表示される
- `なぜ...`では`相談意図: reason_explanation`となり、本人が述べた判断理由が記録されていない知識には、その不足が明示される。LLMが理由を代作しない
- `流量が下がっていた場合...`では`相談意図: condition_comparison`となり、通常範囲の事例と流量低下時の知識が区別して表示される
- 根拠を使った回答では、`search_knowledge → get_context → read_evidence`のように実行したツールが表示される

## 7. 文書から知識を追加する

1. `知識を追加・補足する`を開きます。
2. 入力済みの架空の保全記録1を確認します。
3. `文書から知識候補を抽出（APIを使用）`を押します。
4. 抽出された未承認カードと原文を見比べます。
5. 次の点を確認します。
   - 原文にある観察と確認行動だけが抽出されているか
   - 原因が特定済みのように書き換えられていないか
   - 判断理由や適用範囲が未確認として残っているか
6. 問題がなければ`文書だけで承認候補を作る（API不使用）`を押します。
7. `更新案・実回答比較`へ移動します。
8. `人の確認待ち`で追加内容、fact種別、確定度、未確認事項、原文を照合します。
9. 確認欄を選び、`確認してv1として承認`を押します。

承認前の案は、通常検索や相談の正式知識として使用されません。

**期待される結果**

- 未承認カードに、概ね次の4種類が簡潔に表示される
  - `condition / case_context`: 温度計を交換した後
  - `observation`: 出口温度が高めに表示
  - `check_action`: 別の計器との突合を実施
  - `cause_status`: 表示差の原因は未特定
- `原因、判断理由、適用範囲、確認結果`は未確認のまま残る
- 承認候補の各factに、対応する原文引用が表示される
- v1承認後、知識項目は13件、KB改訂は2になり、確認待ちの案はなくなる

## 8. 文書だけの回答Aを記録する

1. `更新案・実回答比較`で`空の会話で回答Aを実行（APIを使用）`を押します。
2. 回答Aが対象事例のv1を参照していることを確認します。

回答Aは、本人役への聞き取りを行う前の「文書だけの知識」に基づく回答です。

**期待される結果**

- `回答A — succeeded / 対象v1`と表示される
- 実行条件に`model gpt-5.6-luna`、`prompt wg4-prompts-v15`、`空履歴 True`と表示される
- `知識項目13 v1`、由来`document`、文書の原文だけが参照される
- 判断理由と適用範囲は追加されず、未確認事項として残る

## 9. 本人役から理由と適用条件を聞く

1. `知識を追加・補足する`へ戻ります。
2. 入力済みの`本人役の開始発言`を確認します。
3. `不足情報を一つ質問（APIを使用）`を押します。
4. LLMが生成した追加質問を読みます。
5. 本人役の回答欄を確認・編集し、`回答して次の質問へ（APIを使用）`を押します。
6. 判断理由と適用範囲が確認できるまで対話します。二往復程度が目安ですが、回数だけで完了を判断しません。
7. `ここまでの聞き取りで補足案を作る（APIを使用）`を押します。
8. `更新案・実回答比較`で、追加内容と本人役の発言が一致しているか確認します。
9. 確認欄を選び、`確認してv2として承認`を押します。

> 回答欄へ自動入力される例文は、アプリに固定収録された架空教材です。LLMが生成するのは追加質問であり、本人役の回答ではありません。

**期待される結果**

- 追加質問には`LLMがAPIで生成した追加質問`、回答例には`LLMが生成した回答ではありません`と明記される
- 1問目では判断理由、2問目では適用範囲・例外に関する異なる質問が表示されるのが目安。質問文そのものは実行ごとに変わり得る
- 固定回答例の自動挿入は2回答で終了し、3問目は空欄になる。追加回答は任意
- 補足案には、流量と入口温度が通常範囲だったこと、表示変化と実温度変化を切り分ける判断理由、参照条件、流量低下時の例外が含まれる
- `原因、確認結果`は未確認のまま残り、v2承認後のKB改訂は3になる

## 10. 回答Aと回答Bを比較する

1. `更新案・実回答比較`で`空の会話で回答Bを実行（APIを使用）`を押します。
2. `保存済みの実回答 A / B / C`で回答AとBを開きます。
3. `A/Bは同一条件の実回答比較です`と表示されていることを確認します。
4. 回答Bで新たに参照された判断理由・適用条件・発言の出典を確認します。

| 回答 | 対象版 | 主な根拠 |
|---|---:|---|
| A | v1 | 文書に記録された行動・条件 |
| B | v2 | 本人役が補った判断理由・適用範囲・出典 |

文章表現の違いだけでなく、参照されたfactと原文が増えたかを確認してください。

**期待される結果**

- `回答B — succeeded / 対象v2`と表示され、回答Aは`対象v1`のまま残る
- A/Bとも`prompt wg4-prompts-v15`、`空履歴 True`である
- Bの由来が`mixed`となり、判断理由、適用条件、本人役の原文が新たに参照される
- 失敗した過去結果がある場合でも、それを成功結果として置き換えず、状態とエラーコードが区別される

## 11. 回答への指摘を知識へ反映する

1. `更新案・実回答比較`の`回答Bの実候補へ条件を一つ補足`を開きます。
2. 次の発言を入力します。

   ```text
   照合用の計器も、校正が有効か確認する必要があります。
   ```

3. `根拠・条件の更新案を作る（APIを使用）`を押します。
4. `人の確認待ち`で、現行v2から新版v3への差分と原文を確認します。
5. 確認欄を選び、`確認してv3として承認`を押します。
6. `空の会話で回答Cを実行（APIを使用）`を押します。
7. B/Cを比較し、回答Cで追加条件と新しい出典が参照されたことを確認します。

ここで追加するのは「校正が有効か確認する」という確認行動の前提です。「実際に校正が有効だった」という観察ではありません。

**期待される結果**

- 更新案には`action_prerequisite`に相当する条件として`照合用の計器の校正が有効か確認する`が追加される
- 根拠は新しい発言そのものであり、`校正が有効だった`という観察へ書き換えられない
- v3承認後のKB改訂は4になる
- `回答C — succeeded / 対象v3`と表示され、回答Aはv1、回答Bはv2のまま保持される
- Cで校正条件と`聞き取り記録2`の原文が参照される

## 12. A/B/Cの意味

| 回答 | 知識版 | 確認する変化 |
|---|---:|---|
| A | v1 | 文書だけから得られた回答 |
| B | v2 | 本人役の理由・適用条件を追加した後の回答 |
| C | v3 | 回答への指摘を人が承認した後の回答 |

A/B/Cは、同じ質問、モデル、prompt、検索設定、空の会話履歴で実行されます。

承認後の確認では、`エージェントに相談する`で`新しい会話（知識は残す）`を押し、新しい会話の**最初の質問**として次を入力します。

```text
冷却器1の出口温度の表示が高い。温度計交換直後で、冷却水流量と入口温度は通常範囲。何を確認するか？
```

**期待される結果**

- 会話IDが変わり、以前の会話履歴と相談条件は消える
- KB改訂は4のままで、承認済み知識は消えない
- 新しい回答で`知識項目13 v3`が参照され、校正条件と追加した原文が表示される

## 13. 待機中・エラー時の対応

- `待機中`：共有キューへ登録されています。前の処理が終わるまで待ちます。
- `実行中`：API処理中です。画面を再送信せず待ちます。
- `完了`：結果を確認します。
- `失敗`：同じ操作を自動的に再送せず、エラーコードと操作IDを講演者へ伝えます。

A/B/Cの実行が失敗した場合、成功したように扱われず、比較画面に失敗状態が残ります。画面に`新しい操作として回答...を再実行（APIを使用）`が表示された場合だけ、原因確認後に参加者が明示的に押すことで新しい操作として再実行できます。これは自動再送ではありません。

正常に検索して0件だった場合は「0件」と表示されます。検索処理自体が失敗した場合は、0件の結果として扱われません。

このアプリは、API失敗時に固定回答、別モデル、過去の回答へ自動的に切り替えません。

## 14. 終了時

- 必要に応じて`知識を探す`画面から、自分の承認済み知識をJSON形式で保存できます。
- JSONには自分の作業領域の承認済み知識だけが含まれます。
- ブラウザを閉じる前に、必要な結果を確認・保存してください。
